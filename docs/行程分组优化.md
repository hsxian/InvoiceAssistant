# 行程分组算法优化

本次只改 `InvoiceAssistant.Core/Service/Processors/RenameProcessor.cs` 的分组逻辑，未动任何抽取配置。

## 问题

连续多次出差被错误合并成一组：程序把落在锚点区间外的单据按 45 天"就近并入最近的锚点"，一个出差审批单锚点会把间隔数十天的后续行程整段吞掉；孤立返程票也会被粘到上一行程。

## 改动

| 位置 | 改动 | 原因 |
|---|---|---|
| `GroupByAnchors` | 区间外单据改用 `GroupByRoute` / `GroupByDateGap` 独立分段，不再并入锚点 | 杜绝跨行程吞并 |
| `GroupByAnchors` | 末锚点缺 `EndTime` 时，区间上界由 `MaxValue` 改为 `StartTime + 21 天` | 审批单漏抽结束日期时，`MaxValue` 会吞掉之后所有行程 |
| `GroupByRoute` | 新增 `tripClosed`：到达地 == 家即结束当前行程，其后路线票另起一组 | 缺去程的孤立返程票不再污染上一行程 |
| `NearestRange` | `MaxAbsorbGapDays` 45 → 10 | 45 天过宽；扫描显示 7 天会误伤行程末尾单据（F1 0.829），10 天是最紧且零损失的取值 |

`home` 仍取最早一张路线票的出发地：曾试改为 Origin 众数，但返程票的 Origin 是外地，后续行程漏抽去程票时"外地"票数反而占优，会把家判反，故回退。

## 效果

同一验证集（71 份单据 / 63 个唯一内容）的 BCubed：

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 精确率 | 0.634 | 0.875 |
| 召回率 | 0.796 | 0.825 |
| F1 | 0.706 | **0.850** |

两个巨型合并簇已消除，逐次出差可独立成组。第三轮为防复发加固，指标保持 0.850。

## 剩余

误差主要在抽取配置侧（审批单结束日期、财务特殊事项审批日期、驻场日志无配置）与文件夹命名口径、重复内容单据，按约定未纳入本次改动。
